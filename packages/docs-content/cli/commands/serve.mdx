---
title: fab serve
description: Open a local console to start, connect, and close sandboxes.
---

`fab serve` starts Fabricate's managed console on your machine. Sandboxes
shows what is running and which scenario each service loaded. Environments
lists each official environment, the resources and scenarios inside it, and
starts that whole set together. A scenario page shows the seeded records
before you start it. A sandbox keeps running until you close it, or until you
stop `fab serve`.

```bash
fab serve
```

```text
fab: managed console at http://127.0.0.1:4173
```

`--addr` changes the listen address. The default is `127.0.0.1:4173`, which
is only reachable on this machine. `--public-url` is the base clients use
when this process is hosted. Service URLs are published on that base. With
no public URL, they follow the host that opened the console.

```bash
fab serve --addr 0.0.0.0:4173 --public-url https://console.example.com
```

If `--public-url` is set and `--addr` is left at the default, `fab serve`
listens on `0.0.0.0` and the default port. `FAB_CONSOLE_ADDR`,
`FAB_CONSOLE_PUBLIC_URL`, and `FAB_CONSOLE_PROXY` set the same values when
the flags are omitted.

`--ui` also opens the console in a local browser. Leave it off when this
process is a deployed service.

`fab run --ui` serves this same console beside a wrapped command. The
environment that command started stays up until the command exits, and the
console can start more sandboxes next to it. `--ui-addr` and
`--ui-public-url` configure that console the same way.

## Start

**Start all** on an environment starts that manifest, the same set of services
`fab run` would start. Sandboxes lists resources. Open a resource to choose
its scenario by name, then **Start** loads that scenario. The running list
shows each service URL and session id, so several sandboxes of the same
resource stay distinct. Each scenario id opens the seeded records.

There is one Start action. It follows how this process was launched.

Without `--proxy`, Start publishes each service URL on the console host and
an ephemeral bearer token. With `--proxy`, every sandbox starts through the
transparent proxy. Clients keep production hostnames, honor `HTTP_PROXY` and
the generated CA, and the proxy replaces `Authorization` on routed hosts. The
console shows **Running in proxy mode** while that is on.

## Agent index

`GET /.well-known/fabricate` is a JSON document for an agent that is
onboarding this console into another app. It lists every resource and
scenario, every official environment, and the sandboxes that are running.

Each scenario has `name` and `description` for choosing one. Each service has
`storeAs`, `urlName`, and `secretName`. `storeAs` is the name to keep in app
config. `urlName` is the key for the base URL, and `secretName` is the key for
the bearer token. A running sandbox fills in `url` and `secret` with the
values to store. `running` on a scenario lists the sandbox ids currently
using it.

```bash
curl -sS https://console.example.com/.well-known/fabricate
```

The sidebar link **Agent index** opens the same document.

## Connect

The sandbox page shows two ways to use a running sandbox:

- **Connect your app.** Copy the shell exports. Without proxy mode, point each
  client at the service URL and send the bearer token. In proxy mode, export
  the proxy and CA variables and keep the provider's normal hostname.
- **Open in chat.** The sandbox page opens the same prompt in Cursor, Claude,
  ChatGPT, or an email draft. The prompt carries the sandbox connection for
  this machine. It is not a production credential, and it should not be
  committed.

Ports and tokens change every time a sandbox starts. Sandbox processes stay
on loopback. The console publishes them on its own host, so a client that
can open the console can call them. A listen address of `127.0.0.1` still
keeps the console itself on this machine.

Stopping `fab serve` closes every sandbox that console started.
