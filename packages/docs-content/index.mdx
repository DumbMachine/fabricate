Fabricate lets you test the code that talks to outside systems without relying
on a shared test account, hand-written HTTP stubs, or the real provider. It
starts local services that speak a provider-shaped API, loads a known starting
state, runs your application, then tears everything down when the command
exits.

For example, run an email workflow against a seeded Gmail support inbox, let
the workflow search, label, and send mail, and run it again from the exact same
inbox. The shipped Gmail scenario has 12 handcrafted support messages, so a
test can exercise realistic threads instead of a blank or generic fixture.

## What Fabricate is for

- **Integration tests:** exercise API calls, authentication, reads, and writes
  against a repeatable provider state in CI.
- **Local development:** reproduce a support-inbox or data condition without
  changing a real account or coordinating a shared test tenant.
- **Agent and workflow QA:** give an agent a safe, inspectable external system
  to work with, then start the next attempt from the same baseline.
- **Provider SDK compatibility:** keep an SDK's production hostname through
  Fabricate's opt-in, process-scoped proxy when changing its base URL is not
  possible.

Fabricate does not replace your test runner, agent harness, application, or
provider SDK. It provides the disposable systems those tools need to talk to.

## The model

```text
Environment
└── support-mail service
    └── Gmail resource + Acme Corp scenario
```

- **Environment = `fn(services)`:** the disposable lifecycle and isolation
  boundary for everything your command needs.
- **Service = `fn(resource, scenario)`:** one named provider instance, such as
  a support-mail Gmail service started from a chosen dataset.
- **Resource:** the provider-shaped API implementation, such as Gmail today;
  Stripe, GitHub, or another provider can use the same model.
- **Scenario:** versioned data and the initial state for a service—such as a
  Gmail support inbox, or conceptually Stripe data for a Duolingo app versus a
  Netflix app.

The scenario is the baseline, not a scripted sequence of mock responses. The
service starts from that baseline, your application can change it normally,
and the next run starts clean again.

## The first useful run

Install [`fab`](/getting-started) first. Then paste this command; it downloads
the checked-in Gmail environment and lists its seeded inbox. No repository
clone or environment file is required.

```bash
curl -fsSL https://raw.githubusercontent.com/DumbMachine/fabricate/main/environments/acme-gmail.yaml | \
  fab run --environment /dev/stdin -- \
    sh -c 'curl -sS -H "Authorization: Bearer $FAB_SUPPORT_MAIL_TOKEN" \
      "$FAB_SUPPORT_MAIL_URL/gmail/v1/users/me/messages"'
```

`fab run` starts the `support-mail` service, injects
`FAB_SUPPORT_MAIL_URL` and `FAB_SUPPORT_MAIL_TOKEN` into the wrapped command,
and removes the service state afterward. See the [Gmail integration](/resources/integrations/gmail)
for the seeded response and proxy example.

## Direct URL or transparent proxy?

Use the **direct URL** when your application can point its client at a local
base URL. It is the default and simplest option: use the URL and token that
Fabricate injects into the process.

Use the **transparent proxy** when an SDK must keep its normal provider
hostname. Add `--proxy` to `fab run`; Fabricate sets proxy and CA variables
only for the wrapped process, routes the provider hosts declared by the
environment to local services, and blocks everything else unless explicitly
allowed.

## Infrastructure is a separate path

Provider APIs use `fab run` environments. For actual infrastructure such as a
database or Redis, use a container profile with `fab create`. The two paths are
deliberately separate: Fabricate is not pretending that a provider API is a
Docker container, and it is not replacing a real database with a provider
mock.

Continue with [Getting started](/getting-started) to install the CLI, or open
the [Gmail integration](/resources/integrations/gmail) for the runnable API
examples.
