Fabricate is an API sandbox for the services your product already talks to.
Wrap a command: it gets a local Gmail, HubSpot, Intercom, or Asana with known
data, your app talks to it as usual, and the sandbox is gone when the command
exits.

You keep your test runner, your agent, and the official SDK. Fabricate is
the world those tools run against.

## Try it

Install [`fab`](/getting-started) first. Then paste this. No repository clone
or environment file.

```bash
fab run acme-gmail -- \
  sh -c 'curl -sS -H "Authorization: Bearer $FAB_SUPPORT_MAIL_TOKEN" \
    "$FAB_SUPPORT_MAIL_URL/gmail/v1/users/me/messages?maxResults=1"'
```

```json
{
  "messages": [
    {"id": "msg-0028", "threadId": "thr-refund"}
  ],
  "nextPageToken": "1",
  "resultSizeEstimate": 27
}
```

That is the Acme support inbox: 28 handcrafted messages, one of them in
spam/trash, so a default list reports 27. `fab run` started Gmail, handed the
command a URL and a token, and removed the state afterward. Run it again and
`msg-0028` is back.

Python, Node, and Rust clients that wrap the same way live in
[`examples/`](https://github.com/DumbMachine/fabricate/tree/main/examples).

## Why teams use it

| You are building | What you run against |
| --- | --- |
| Mail, CRM, helpdesk, or billing as a core feature | A known Gmail, HubSpot, or Intercom in every test |
| An agent that files, replies, and updates records | A messy tenant that resets after each eval |
| A team of engineers and CI jobs | Per-run sandboxes, not a shared QA inbox |
| A feature that needs HubSpot today | The wrap command, no ticket to finance or the vendor |

### Test integrations that are the product

If the product *is* mail, CRM, helpdesk, or billing, the connector is not a
side channel you can stub with `{"ok": true}`. Users judge you on search,
labels, deal stages, and whether a send actually lands.

Fabricate gives those tests the same API your SDK already uses, with a
known tenant. Wrap `npm test` or `pytest` with `fab run acme-gmail` and
every run sees the same inbox. The [Gmail](/resources/integrations/gmail),
[HubSpot](/resources/integrations/hubspot), and
[Asana](/resources/integrations/asana) pages list what each API can do;
the [example apps](https://github.com/DumbMachine/fabricate/tree/main/examples)
are the same wrap with application code.

### Put agents in the world customers actually live in

Customers do not live in a sanitary CRM. They have duplicates, stalled
deals, two people with the same name, an invoice in mail that the board never
closed, and a chat thread that disagrees with the ticket.

If you evaluate an agent against an empty HubSpot, you learn whether it can
create a deal. You do not learn whether it refunds INV-4812 twice, emails
the wrong Mei Chen, or closes a conversation before reading the Gmail thread.

[Acme Support Desk](/resources/environments/acme-support-desk) is one company
across Gmail, Intercom, Asana, and HubSpot. Records join on purpose. Some of
them conflict on purpose. That is the dataset to score an agent that promised
to do real work after the user clicked **Connect Gmail**.

### Give every engineer their own sandbox

A five-person team shipping a Gmail feature does not need five Workspace
inboxes, a shared QA HubSpot that someone reset at 4pm, and a rotation for
who may send mail this week.

Each `fab run` is its own sandbox. Engineers do not share a tenant. Parallel
CI jobs do not fight over the same deal. A new hire runs the same command on
day one.

### Ship without a vendor test tenant

A "real" HubSpot sandbox, Intercom workspace, or Gmail add-on test user is
often a ticket: billing, legal, a partner manager, a two-day wait. The PR is
a 20-line sync.

Wrap the app locally. Nobody has to provision the account. The vendor does
not have to approve a developer tenant. The next engineer is not blocked on
someone else's queue.

### Let the agent write, then rewind

The products that matter now connect to Gmail or HubSpot and then *act*:
draft and send, label the thread, patch the deal, comment on the task. That
is only testable if those writes are real API calls, inspectable, and
reversible.

The agent can send mail and close a deal. `fab logs` shows the redacted
trace. The next run starts from the same baseline, so an eval score means
the same thing on the next attempt.

- **Environment** — the sandbox. One lifecycle for everything the command
  needs.
- **Service** — one named provider in that sandbox, such as `support-mail`.
- **Resource** — which API that service speaks: Gmail, HubSpot, Asana,
  Intercom.
- **Scenario** — the starting data. Acme's support inbox is a different world
  from an empty mailbox.

The scenario is a baseline, not a script of fake responses. Your app can
change it. The next run starts clean.

## Direct URL or `--proxy`?

If your app can take a base URL, use the URL and token Fabricate injects.
That is the default.

If the official SDK already calls `gmail.googleapis.com`, add `--proxy`.
Fabricate intercepts those hosts for that process only. Use a direct URL when
the client pins certificates or ignores proxy settings.

[Getting started](/getting-started) has the wrap commands.
[Example apps](https://github.com/DumbMachine/fabricate/tree/main/examples)
show both modes. [Agent and workflow QA](/guides/agent-workflows) is for
workers and local agents.
